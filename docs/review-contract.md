# レビュー契約

レビューの指摘をどう記録・処置し、何をもって変更を受け入れてよいとするかの **原典**。
AGENTS.md・レビュースキル (`.agents/skills/code-review/SKILL.md`)・git hook (`.githooks/`)・
Claude Code hook (`.claude/hooks/review-gate.sh`)・判定ツール (`tools/review-gate/`) はここを参照し、
規則を転記しない。規則を変えるときはこのファイルを先に変え、判定ツールを追従させる。

生成元: foo-skills 3.0.0 `skills/bootstrap/resources/review-contract.md` (経緯は `.contexts/bootstrap-decisions.md`)。
このファイルは基準ファイルで、変更には CODEOWNERS の承認が要る (`docs/remote-acceptance.md`)。

## なぜ件数ではなく指摘の台帳か

- LLM レビューは非決定的。前回出た指摘が今回出ないのは「直った」とは限らず、「今回は見落とした」だけのことがある。件数だけの記録では両者を区別できない
- 件数で完了を判定すると、レビューのたびに判定を取り直すことになり「指摘 → 修正 → 新しい指摘」のループが終わらない。完了は個々の指摘の処置が積み上がった結果として決める
- 修正が新しい問題を生んだのか、前からあった問題を後で見つけたのかを区別しないと、ワークフローのどこを直すべきか分からない

## 台帳

- 置き場所: `$(git rev-parse --git-common-dir)/review-ledger/ledger.json`。リポジトリ外 (`.git/` 配下) に置き、追跡しない。台帳をコミットするとレビュー対象の差分そのものが変わるため
- 書き込めるのはレビュー主体だけ。レビュー主体は `node tools/review-gate/src/cli.ts record --file <round.json>` で 1 回分のレビュー (ラウンド) を追記する。**実装側による手書き・改変は禁止**。実装側は修正と、解消を示す証拠を渡す
- 各ラウンドは対象 diff のハッシュ・スコープ (`commit` = staged 分 / `push` = `origin/main` との merge-base から HEAD まで)・実行時刻・レビュー主体・出力が正常だったかを持つ。ハッシュは `cli.ts hash --scope <scope>` が返す値で、`record` は現在の diff と一致しないラウンドを拒否する
- 台帳は diff をまたいで引き継ぐ。再レビューは既存の指摘の解消確認から始める

### 指摘が持つもの

| 項目 | 内容 |
|---|---|
| ID | 台帳の中で一意。同じ問題の言い換えは新しい ID を作らず、既存の指摘を更新する |
| 対象 | ファイル・範囲と、レビューした diff のハッシュ |
| 根拠 | 違反している要件・受け入れ条件・規約・設計原則 (AGENTS.md / `.contexts/` / `openapi/openapi.yaml` の該当箇所) と、それを示す証拠 (コード、再現手順、仕様) |
| 重大度 | Critical / Important / Minor と、その理由 |
| 状態 | 下記のライフサイクル |
| 処置の根拠 | 却下・保留・解消・エスカレーションの理由と証拠 |
| 由来 | 修正が生んだ指摘なら、どの指摘への修正か。確認済み・推定・不明を区別し、不明を推測で埋めない |

## ライフサイクル

| 状態 (`status`) | 意味 |
|---|---|
| 未処置 (`open`) | 新規、または新しい証拠で再開した |
| 修正済み・未確認 (`fixed_unverified`) | 実装側が修正したが、レビュー側がまだ確かめていない |
| 解消 (`resolved`) | レビュー側が解消を確かめた |
| 却下 (`rejected`) | 誤検知・根拠不足。仕様・テスト・反例などの証拠で裁定した |
| 保留 (`deferred`) | 妥当だが今回の受け入れを妨げない。別タスクとして記録する。**Critical には使えない** |
| エスカレーション (`escalated`) | 委任された範囲では判断できない (意図の衝突、権限の不足、許容範囲を超える不確実性)。判断依頼を積み、`decisionRef` で参照する |

- 解消の確認はレビュー側が行う。実装側の「直しました」は `fixed_unverified` 止まり
- 解消・却下した指摘でも、新しい証拠や修正による再発があれば **同じ ID で** `open` に戻す。新しい証拠を示さずに同じ指摘を繰り返さない (再開には証拠が必須)
- `open` 以外の状態への遷移には理由 (`resolution`) が必須

## 完了の判定

完了は「変更を受け入れてよいか」の判定であり、「作業を続けてよいか」の判定ではない。完了しても、人間の承認なしでマージしてよいとは限らない (`docs/remote-acceptance.md`「人間の承認なしでマージしてよい変更」)。

- 完了は台帳の状態と決定的ゲート (format / lint / 型 / テスト / アーキテクチャテスト) の結果で判定する。レビュー主体の「LGTM」宣言は完了ではない
- **現在の diff をレビューしたラウンドがない = レビューしていない = 不合格**
- **レビューの出力がない・壊れている (`outputOk: false`) のは処理失敗であって「指摘なし」ではない = 不合格**
- Critical は「解消」か「証拠付きの却下」だけが通る。未処置・修正済み (未確認)・エスカレーション中が 1 件でもあれば完了にしない
- Important はすべてに処置 (解消・却下・保留) と根拠がある。エスカレーション中は完了にしない
- Minor は任意
- Important を却下・保留したときは、台帳が追跡されないため、コミットメッセージ本文にも理由を書く

## 作業の継続と受け入れ

人間の判断待ちを、仕事を止める理由にしない (AGENTS.md「Asking for decisions」)。

- エスカレーション中の指摘は、判断依頼 (GitHub Issue、ラベル `needs-decision`) が積まれ、指摘から `decisionRef` (例: `#123`) で参照されていれば、作業ブランチへの commit / push を止めない。参照のないエスカレーションは未処置と同じく止める
- エスカレーションにするのはレビュー主体で、委任範囲内で決められない理由を確かめてから行う。直せる欠陥をエスカレーションで先送りしない。例外が効くのはその指摘だけで、決定的ゲートとレビュー実施の確認は通常どおり必要
- 裁定を待つ間は、判断に依存しない作業を進めるか、置き換えやすい暫定案で作る。暫定案で進めたことと差し替え方は判断依頼に書く
- 受け入れ (リモートの受け入れ判定、マージ) は裁定が出るまで通らない。暫定案のまま完了にしない。レビュー指摘に由来しない判断待ちも、その変更が依存するなら重大度に関係なく同じく扱う
- 裁定が出たら、依頼の前提が今も有効か確かめてから適用する。前提が変わっていれば依頼を更新して判断を求め直す

## 再レビューの範囲

- 初回は変更全体を見る
- 2 回目以降は、既存の指摘の解消確認、前回からの差分、修正の影響範囲を中心に見る。新しい問題を見つけることは妨げないが、新規指摘は「前からあった見落とし」か「修正が生んだもの」かを由来に記録する
- 判断に迷う指摘は、再実行して残るかどうかではなく、証拠 (テスト・反例・仕様) で処置する。再実行で出なかったことは解消でも却下の根拠でもない
- 同じカテゴリの指摘が 2 回続いたら、個別対応をやめて全件スイープする

## 基準の改訂

レビュー中に基準 (規約・受け入れ条件・検証器) の不適切さに気づいたら、改訂の提案は正当な仕事である。ただし指摘を閉じる都合で基準を緩めない。改訂には根拠・権限・適用範囲を示し、改訂前の指摘と判定の履歴は消さない。基準ファイルの改訂は CODEOWNERS の承認を経て有効になる。

## 独立性

- 初回の独立評価には、承認済みの要件・制約・設計判断を渡し、実装時の思考の経緯・自己評価・説得のための説明は渡さない
- 解消確認では、変更内容・再現手順・検証結果を渡し、レビュー側が独立に確かめる。証拠は渡すが、結論は渡さない
- 同じ会話の中で自分の実装を自分でレビューしない。Claude Code では `code-reviewer` サブエージェント、Codex では別セッションを使う。別のコンテキストのレビュー主体を使えないときは、レビューは未実施として扱う
- 複数のレビュー主体を使うときは、まずそれぞれが独立に評価し、指摘を証拠で確かめてから、食い違った点だけを突き合わせる。解消しない反対意見は証拠への参照とともに台帳に残し、まとめる側が黙って消さない

## ゲートが区別するケース

判定ツールのテスト (`tools/review-gate/test/evaluate.test.ts`) で次を確かめている。ゲートを変えたら、このケースが保たれていることを確かめる:

1. 前回の Critical が今回のレビューで出なかった → 解消の確認がなければ止まる
2. 証拠付きで却下した Important → 止まらない
3. 解消済みの Critical が新しい証拠で再開した → 止まる
4. Critical をエスカレーションし判断依頼を積んだ → commit / push は止まらず、受け入れは裁定が出るまで通らない。判断依頼が積まれていなければ止まる
5. レビューの出力がない → 止まる (指摘なしとして通さない)

## この契約が保証しないこと

台帳と hook は、実装しているエージェント自身が書き換えられる場所にある。この契約が保証するのは手元の運用の規律までで、改ざんへの耐性はない。実装エージェントの権限で変えられない受け入れ保証は `docs/remote-acceptance.md` が持つ。
